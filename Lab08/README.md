N = 8, K = 17, a = 2, b = 0, c = 3

# Лабораторна робота №8: Алгоритми пошуку та їх порівняння

## Персональні параметри варіанта
- **N = 8**, **K = 17** (літера **М**)
- **a = 2**: масив `Student[]` (100 000 записів, бали `0–100`), порівняння `cmp` лише за полем `Score`
- **b = 0**: основний запит пошуку межі — індекс першого входження `X`
- **c = 3**: додатковий алгоритм — експоненційний пошук (`ExponentialSearch`)
- **X = 67** (`K + 50`), **Y = 77** (`K + 60`), відсутнє значення — бал **101**

---

## Завдання 1 · Лінійний пошук (`LinearSearch`)
- **Значення X (`Score = 67`):** індекс `66397`, порівнянь `66398`
- **Перший елемент масиву (`Score = 0`):** індекс `0`, порівнянь `1`
- **Відсутнє значення (`Score = 101`):** індекс `-1`, порівнянь `100000`

**Пояснення:** Третій запит виявився найдорожчим (`100 000` порівнянь), оскільки лінійний пошук не використовує впорядкованість масиву і змушений перевірити кожен елемент до самого кінця, щоб переконатися у відсутності шуканого балу.

---

## Завдання 2 · Бінарний пошук (`BinarySearch`) та чотири поломки

### Результати правильного `BinarySearch`:
- **Значення X (`Score = 67`):** індекс `67186`, порівнянь `6`
- **Перший елемент масиву (`Score = 0`):** індекс `780`, порівнянь `7`
- **Відсутнє значення (`Score = 101`):** індекс `-1`, порівнянь `17`

### Прояв чотирьох поломок:
1. **`while (lo < hi)` замість `while (lo <= hi)`:** на масиві `[10, 20, 30]` при пошуку `Score = 30` алгоритм повертає `-1` (порівнянь: `1`). Коли звуження меж доходить до останнього кандидата (`lo == hi == 2`), умова `lo < hi` стає хибною і цикл завершується, не перевіривши цей елемент.
2. **`lo = mid` замість `lo = mid + 1`:** на масиві `[10, 20, 30]` при пошуку `Score = 30` програма потрапляє в нескінченний цикл (`[крок 1: lo=0, hi=2, mid=1] [крок 2: lo=1, hi=2, mid=1] [крок 3: lo=1, hi=2, mid=1] ...`). Коли `hi = lo + 1`, цілочисельне ділення дає `mid = lo`, тому межі перестають рухатися.
3. **`mid = (lo + hi) / 2`:** на `100 000` елементів працює коректно (`індекс = 67186`, `порівнянь = 6`), оскільки `99 998 + 99 999 = 199 997` значно менше за `int.MaxValue` (`2 147 483 647`). Переповнення типу `int` у від'ємне число виникає лише при розмірі масиву від **1 073 741 824** елементів і більше.
4. **Масив не відсортований:** зі `100` запитів гарантовано наявних у масиві студентів алгоритм повернув `-1` **87** разів, оскільки на кожному кроці відкидає половину елементів, хибно розраховуючи на їх впорядкованість.

## Завдання 3 · Пошук межі (`FindBoundary`)
- **Основний запит (`b = 0` — індекс першого входження `X = 67`):** `66397` (порівнянь: `17`)
- **Кількість елементів, рівних `X = 67`:** `1020` (сумарно порівнянь за два бінарні пошуки меж: `34` проти `100 000` при лінійному підрахунку)

**Чому кількість порівнянь не залежить від кількості елементів, рівних X:** Пошук межі не зупиняється на першому збігу і не перебирає дублікати послідовно — він завжди ділить інтервал індексів `[0; n]` навпіл до сходження меж `lo == hi`, виконуючи фіксовані $\lceil \log_2(n + 1) \rceil = 17$ порівнянь для кожної межі.

**Перевірка на умові, не узгодженій з порядком (`s => s.Score % 7 == 0`):** Метод повернув індекс `100000` (`a.Length`), тоді як реальний перший кратний 7 елемент знаходиться на індексі `0` (`Score = 0`). Відповідь **неправильна**, оскільки предикат `Score % 7 == 0` не є монотонним на масиві, відсортованому за зростанням `Score` (значення `true` і `false` чергуються).

## Завдання 4 · Експоненційний пошук (`ExponentialSearch`, `c = 3`)

| Запит | Класичний бінарний (порівнянь) | Експоненційний (порівнянь) |
| :--- | :---: | :---: |
| 1. Значення X (`Score = 67`, індекс `66612`) | `6` | `23` |
| 2. Перший елемент (`Score = 0`, індекс `0`) | `7` | `1` |
| 3. Відсутнє значення (`Score = 101`) | `17` | `34` |

**Аналіз:** Експоненційний пошук виграє у звичайного бінарного тоді, коли шуканий елемент знаходиться на самому початку масиву (для індексу `0` він витратив лише `1` порівняння проти `7` у класичного бінарного, а поблизу початку працює за $O(\log k)$, де $k$ — позиція елемента). Натомість для елементів у другій половині масиву (`66612`) або для відсутніх значень (`101`) він програє (`23` проти `6` та `34` проти `17`), бо витрачає додаткові порівняння на стрибки степенями двійки перед запуском бінарного пошуку.

## Завдання 6 · Висновок

1. **Зміряна точка окупності проти лекційних 34 запитів:** Навіть при `q = 100` запитах лінійний перебір (`0,373 мс`) виявився швидшим за попереднє сортування з бінарним пошуком (`12,570 мс`), тобто реальна точка окупності становить понад **3 000 запитів**, що набагато **більше** за теоретичні `34`. Лекційна оцінка $2 \log_2 n$ рахує лише кількість порівнянь елементів, тоді як на практиці `Array.Sort` для `100 000` посилань `Student` виконує багатократні виклики делегата `Func<Student, Student, int>`, переміщення вказівників у пам'яті та створює промахи кешу процесора (cache misses), тоді як лінійний прохід читає масив послідовно з високою швидкістю апаратної передвибірки.
2. **Два питання, на які відповідає бінарний пошук, а `HashSet`/`Dictionary` — ні:**
   - Знайти кількість студентів або всі записи, чий бал потрапляє в інтервал `[67; 77]` (пошук за діапазоном / межами `LowerBound` та `UpperBound`).
   - Знайти найближчий наявний бал до заданого числа (наприклад, перший бал $\ge X$), якщо точного збігу в базі немає.
3. **Потік даних, де масив змінюється після кожного запиту:** Найкраще обрати **хеш-структуру** (`Dictionary` або `HashSet`). Лінійний перебір працює за $O(n)$, постійне пересортування масиву перед бінарним пошуком коштуватиме $O(n \log n)$ на кожне оновлення (або $O(n)$ на вставку зі зсувом елементів), тоді як хеш-таблиця забезпечує вставку, видалення і пошук за $O(1)$ у середньому.
